# Plan — Terraform Provider for mint-ca

## Objective
Build `terraform-provider-mintca`, letting infrastructure be declared against
mint-ca (`github.com/Imnotndesh/mint-ca`) the same way it's declared against
any cloud API: `mintca_ca`, `mintca_provisioner`, `mintca_certificate`, etc.
as Terraform resources, managed via `terraform apply`/`plan`/`destroy`.

This is a **separate Go module/repo**. It talks to mint-ca purely over its
REST API (`docs/Api.md`) — do not attempt to import any `mint-ca/internal/...`
Go package (unexported, and the wrong layer of abstraction for a Terraform
provider anyway). Read `docs/Api.md` and `docs/Setup.md` in full before
starting; this plan is a map of that doc, not a replacement for it.

## Ground rules
- Use [`terraform-plugin-framework`](https://github.com/hashicorp/terraform-plugin-framework)
  (the current, non-deprecated SDK — do NOT use the legacy
  `terraform-plugin-sdk/v2`, which HashiCorp is phasing out).
- Repo layout follows HashiCorp's
  [provider scaffolding](https://github.com/hashicorp/terraform-provider-scaffolding-framework):
  ```
  terraform-provider-mintca/
    main.go
    internal/provider/
      provider.go              # the Provider itself (schema: endpoint, api_key, ca_cert, insecure)
      client/                  # hand-written REST client (can share design with the mca CLI's client package, but this is a separate module — do not attempt a shared Go module dependency between the two unless you deliberately set up a shared `mintca-go-client` module first; simplest is to duplicate the ~10 client methods you need, they are small)
      ca_root_resource.go
      ca_intermediate_resource.go
      provisioner_resource.go
      profile_resource.go
      policy_resource.go
      certificate_resource.go   # via POST /api/v1/certs/issue or /sign
      approval_rule_resource.go
      apikey_resource.go
      eab_key_resource.go
      *_data_source.go          # read-only lookups, e.g. mintca_ca (by name), mintca_provisioner
    examples/
      provider/provider.tf
      resources/mintca_ca/resource.tf
      ...
    docs/                       # generated by `tfplugindocs`, do not hand-write
  ```
- Go version: match mint-ca's (`go 1.25.0`) or newer.
- `go build ./...`, `go vet ./...`, `go test ./...` clean before every commit.
  Acceptance tests (`TF_ACC=1 go test ./...`, using
  `terraform-plugin-testing`'s `resource.Test`) require a real mint-ca
  instance reachable at `MINTCA_ENDPOINT`/`MINTCA_API_KEY` env vars — gate
  them behind `TF_ACC` exactly as the framework's convention expects, so
  plain `go test ./...` (no `TF_ACC`) stays hermetic and fast.

## Provider configuration schema
```hcl
provider "mintca" {
  endpoint = "https://ca.internal:8443"   # or MINTCA_ENDPOINT
  api_key  = var.mintca_api_key           # or MINTCA_API_KEY (mark sensitive!)
  ca_cert  = file("ca.pem")               # optional PEM to trust; or MINTCA_CA_CERT (path)
  insecure = false                        # or MINTCA_INSECURE — skip TLS verify, dev only
}
```
- `api_key` must be declared `Sensitive: true` in the schema so it never
  appears in plan/apply output or the state file's human-readable diff (it
  is still stored in state — that's unavoidable for any provider needing
  credentials to manage a resource's lifecycle; document this in the
  provider's docs and recommend a remote encrypted state backend).
- Resolve config the standard Terraform way: explicit HCL argument wins, then
  the matching environment variable, then error if neither is set.
- Build one shared `*client.Client` in `provider.Configure()` and store it in
  `resp.ResourceData` / `resp.DataSourceData` for every resource/data source
  to retrieve via `req.ProviderData.(*client.Client)`.

## Resource-by-resource mapping

For each resource below: **Create** maps to the documented `POST`, **Read**
to the matching `GET`, **Update** either to a documented `PUT` where one
exists or is unsupported (`RequiresReplace` on every attribute) where mint-ca
has no update endpoint, **Delete** to the documented revoke/delete endpoint
(mint-ca rarely hard-deletes rows — "delete" in Terraform terms usually means
"revoke", which is the right final state for a certificate authority anyway).

### `mintca_ca` (root or intermediate CA)
- Maps to `POST /api/v1/ca/root` or `POST /api/v1/ca/intermediate`
  (`docs/Api.md` §1.1) depending on whether `parent_ca_id` is set — implement
  as **one resource** with an optional `parent_ca_id` attribute, branching
  internally on Create, since Terraform users think of both as "a CA".
- Schema attributes: `id` (computed, UUID), `name` (required, `RequiresReplace`
  — mint-ca has no rename endpoint), `common_name` (required, `RequiresReplace`),
  `organization`/`country`/`state`/`locality` (optional, `RequiresReplace`),
  `key_algo` (optional, default `ecdsa-p256`, `RequiresReplace`), `ttl_days`
  (optional, default 3650, `RequiresReplace`), `parent_ca_id` (optional,
  `RequiresReplace`), `max_path_len` (optional, only meaningful with
  `parent_ca_id` set), `status` (computed), `cert_pem` (computed), `not_before`/
  `not_after`/`created_at` (computed).
- Read: `GET /api/v1/ca/{caID}`. If it 404s, call `resp.State.RemoveResource(ctx)`
  (standard "was deleted out of band" handling) rather than erroring.
- Delete: `PUT /api/v1/ca/{caID}/revoke`. mint-ca never hard-deletes a CA row;
  document this clearly — `terraform destroy` revokes, it does not erase.
- **Do not** implement Update — every field forces replacement. mint-ca CAs
  are immutable identity objects by design (rekey/cross-sign are separate,
  deliberate lifecycle actions modeled as separate resources below, not as
  an "update" of the CA resource).

### `mintca_ca_rekey` (models `POST /api/v1/ca/{caID}/rekey`)
This is unusual: rekeying **creates a new CA row** while preserving the
logical identity (`logical_ca_id`, see Api.md §1.1's `rekey` docs). Model it
as its own resource, not an update to `mintca_ca`, so Terraform's plan output
correctly shows "a new CA object is being created" rather than silently
mutating the original `mintca_ca` resource's `id` out from under any
`mintca_provisioner` resources referencing it (those keep working
automatically server-side via `logical_ca_id`, per the docs — Terraform
config referencing the *original* `mintca_ca.id` will still work after a
rekey done via a *separate* `mintca_ca_rekey` resource, exactly mirroring how
the API itself behaves).
- Attributes: `ca_id` (required, `RequiresReplace` — the CA being rekeyed),
  `key_algo`/`ttl_days` (optional, `RequiresReplace`), `id`/`new_ca_id`/
  `cert_pem`/`not_before`/`not_after` (computed, the new CA row's data).
- Create only; Delete is a no-op (there is nothing to "undo" about a
  historical rekey — warn in the docs that destroying this resource just
  forgets it in Terraform state, it does not un-rekey anything server-side).

### `mintca_provisioner`
- Maps to §1.3. Attributes: `id` (computed), `ca_id` (required,
  `RequiresReplace`), `name` (required, `RequiresReplace`), `type` (required,
  `RequiresReplace`), `config` (optional, a `jsontypes.Normalized` attribute —
  from `terraform-plugin-framework-jsontypes` — so arbitrary JSON config
  round-trips cleanly and diffs semantically rather than byte-for-byte),
  `policy_id`/`profile_id` (optional, mutable — see Update below), `status`
  (computed or settable via a dedicated boolean `enabled` attribute).
- Update: mint-ca only exposes `PUT .../enable` and `PUT .../disable` (§1.3)
  — no generic field-update endpoint. Model `enabled` (bool) as the only
  updatable attribute, calling the matching endpoint on change; every other
  attribute change forces replacement. If `policy_id`/`profile_id` need to be
  mutable later, check whether mint-ca has grown a generic
  `PUT /api/v1/provisioners/{id}` by the time you implement this — if not,
  mark them `RequiresReplace` too and note the limitation in the resource's
  docs.
- Delete: mint-ca has no provisioner delete endpoint as of this writing —
  confirm current API surface; if still absent, Delete should call disable
  and document that Terraform "destroy" leaves a disabled row behind, same
  spirit as the CA resource.

### `mintca_profile` (§1.4)
- Full CRUD exists (`POST`/`GET`/`PUT`/`DELETE /api/v1/profiles/{id}`) — a
  standard mutable resource. Attributes mirror the request/response body:
  `id` (computed), `name` (required), `allowed_key_algos` (optional list),
  `min_ttl_seconds`/`max_ttl_seconds` (optional int64), `require_san`
  (optional bool), `allow_wildcard` (optional bool).
- Update: `PUT`, full replace-body semantics (send every field each time,
  matching what the API expects — check the current handler in
  `docs/Api.md` for whether partial updates are supported; if the API
  requires the full object on `PUT`, the provider's Update must read current
  state and merge in only the changed attributes before sending).

### `mintca_policy` (§1.4)
Same shape as `mintca_profile`: full CRUD, standard mutable resource. Read
the exact request/response fields from `docs/Api.md` §1.4's policy section
(policy OIDs, CPS URI, TTL/key-algo constraints, CA/provisioner scoping) and
mirror them 1:1 as schema attributes.

### `mintca_csr_approval_rule` (§1.15)
Full CRUD (`POST`/`GET` list+filter/`PUT`/`DELETE
/api/v1/approval/csr-rules/{ruleID}`). Attributes: `id` (computed),
`provisioner_id` (required, `RequiresReplace`), `name` (required),
`allowed_common_names` (optional list of regex strings), `allowed_dns`
(optional list of regex strings), `max_ttl_seconds` (optional int64),
`enabled` (optional bool, default true).

### `mintca_eab_key` (§1.5)
Create + list + delete only (no update — EAB keys are typically
one-shot/rotated, not edited). Attributes: `id`/`key_id`/`hmac_key`
(computed, **sensitive** — the HMAC key is shown once; store it in Terraform
state as `Sensitive: true` and document loudly that Terraform state is the
only place it will ever be recoverable from after creation, so state must be
protected/encrypted), `provisioner_id` (required, `RequiresReplace`).

### `mintca_api_key` (§1.6)
Create + list + rotate + delete. Model rotation as a **separate** resource
(`mintca_api_key_rotation` or similar) rather than an in-place Update of
`mintca_api_key`, for the same reason as CA rekey: rotating produces a new
raw secret value that Terraform needs to surface distinctly, and conflating
it with a generic "update" obscures that a secret materially changed.
`mintca_api_key` attributes: `id` (computed), `name` (required,
`RequiresReplace`), `scopes` (required list, `RequiresReplace`), `ca_id`
(optional, `RequiresReplace`), `expires_at` (optional, `RequiresReplace`),
`raw_key` (computed, **sensitive**, only populated immediately after Create —
on a subsequent `terraform plan`/`refresh`, mint-ca cannot return the raw key
again since it only stores the hash; leave the attribute as `Sensitive` and
document that if it's lost from state, only a new key/rotation recovers
access).

### `mintca_certificate` (§1.2, `POST /api/v1/certs/issue`)
This is the most consequential resource, since Terraform users will manage
real TLS certificates through it.
- Attributes: `id` (computed), `ca_id` (required, `RequiresReplace`),
  `provisioner_id` (required, `RequiresReplace`), `common_name` (required,
  `RequiresReplace`), `sans_dns`/`sans_ip`/`sans_email`/`sans_uri` (optional
  lists, `RequiresReplace`), `spiffe_id` (optional, `RequiresReplace`),
  `ttl_seconds` (required, `RequiresReplace`), `key_algo` (optional,
  `RequiresReplace`), `server_auth`/`client_auth` (optional bool,
  `RequiresReplace`), `profile` (optional, `RequiresReplace`), `metadata`
  (optional `jsontypes.Normalized`, `RequiresReplace`), `cert_pem`/`key_pem`/
  `chain_pem` (computed, **`key_pem` sensitive**), `not_before`/`not_after`
  (computed).
- There is deliberately **no in-place renewal**: every attribute forces
  replacement, so a Terraform-managed cert is immutable — to renew, taint or
  otherwise trigger recreation (or add a `keepers`-style
  `triggers_replace` attribute, e.g. a `time_rotating` resource's ID passed
  in, following the same pattern the `tls_cert_request` / `acme_certificate`
  community providers use for scheduled rotation). Document this pattern
  explicitly in `examples/resources/mintca_certificate/resource.tf` with a
  worked example using `terraform-provider-time`'s `time_rotating`.
- Read: `GET /api/v1/certs/{certID}`. If the cert is revoked or 404s,
  remove from state (same as the CA resource).
- Delete: `PUT /api/v1/certs/{certID}/revoke`.
- Do **not** attempt to model `POST /api/v1/certs/sign` (client-submitted
  CSR) as the same resource — client-generated keys don't fit Terraform's
  "provider owns the full lifecycle" model well (Terraform would never see
  the private key). If a CSR-signing resource is wanted later, model it
  separately as `mintca_certificate_signing` taking `csr_pem` as an input
  and never exposing a `key_pem` output attribute (there is none — the key
  never left the client in the real flow either).

## Data sources
Provide read-only lookups mirroring the corresponding resource's Read, for
referencing infrastructure Terraform doesn't manage:
- `data.mintca_ca` (by `id` or `name`)
- `data.mintca_provisioner` (by `id`)
- `data.mintca_profile` (by `id` or `name`)
- `data.mintca_renewal_status` (wraps `GET /api/v1/renewal/status`, §1.16 —
  useful for a `terraform plan` step that fails/warns if certs are near
  expiry; expose `due_count`/`expiring_soon_count`/`expired_count`/
  `revoked_count` and the full per-cert list as a computed attribute)

## Client package
Hand-write the ~15 REST calls needed (same principles as the `mca` CLI's
client — see `docs/plans/cli-mca.md`'s "The API client" section for the
exact conventions: `Authorization: Bearer`, `DisallowUnknownFields`-safe
request bodies, uniform `{"error": "..."}` decoding, context-aware). Do not
attempt to share a Go module between this provider and the `mca` CLI unless
a dedicated `mintca-go-client` module is deliberately created first as a
separate, versioned dependency both can import — until then, duplicating the
small client is simpler and avoids coupling two independent release
cadences.

## Testing requirements
- Unit tests for the client package exactly as described in the CLI plan
  (`httptest.NewServer`, no live server).
- Acceptance tests (`internal/provider/*_test.go`, `TF_ACC=1`) using
  `terraform-plugin-testing`'s `resource.Test` / `resource.TestStep` for
  every resource: create, plan-is-empty-after-apply (`PlanOnly: true` check),
  update where applicable, import (`ImportState: true` — every resource
  should support `terraform import mintca_ca.example <uuid>`), and destroy.
  These require `MINTCA_ENDPOINT`/`MINTCA_API_KEY` pointed at a real (can be
  a local Docker) mint-ca instance with at least the bootstrap root CA/API
  key already set up — document the required `docker run` / `docker-compose`
  snippet in `CONTRIBUTING.md`, referencing `docs/Setup.md`'s Docker section.
- `tfplugindocs generate` must run clean (schema descriptions populated for
  every attribute — this is also what makes `terraform-plugin-docs`-based
  registry pages readable, so treat missing descriptions as a review
  blocker).

## Acceptance bar
- `go build ./...`, `go vet ./...`, `go test ./...` (non-acceptance) clean.
- `terraform fmt -check` clean on every file under `examples/`.
- At minimum: `mintca_ca`, `mintca_provisioner`, `mintca_certificate`,
  `mintca_profile` implemented with passing acceptance tests, before calling
  v0.1.0 done. The remaining resources (policy, approval rule, EAB key, API
  key, rekey) can land incrementally in later releases — call this out in
  the README's "Resource coverage" table with a done/planned column, mirroring
  the style of this very document.
- Publish to the Terraform Registry (requires a GPG-signed release via
  `goreleaser` per HashiCorp's publishing docs) once acceptance tests are
  green for the v0.1.0 resource set.

## Out of scope for v0.1.0
- SSH CA resources (§1.11) — large surface, defer to v0.2.0.
- ACME-related resources — ACME is a protocol for *clients* to obtain
  certs, not something Terraform manages server-side; skip entirely.
- Multi-tenant scoping (`docs/plans/multi-tenancy.md`) — if/when mint-ca
  gains tenant-scoped resources, the provider's config schema will need a
  `tenant_id` or per-tenant API keys; not needed until that lands.
